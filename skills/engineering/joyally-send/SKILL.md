# Joyally Send

这是 Codex 的默认工程完成闭环：在当前 checkout 内理解目标、实现、验证、复查、修正并按既有授权交付。不要把“代码写完”当作任务完成，也不为日常任务新增 PR 或分支编排。

## 完成契约

开始时读取项目约定、源码、配置、当前运行状态和 Git 边界，明确用户真正要得到的结果。目标足够清楚时直接推进；普通实现选择采用最小、可验证且符合现有架构的方案，并在进度中说明关键假设。只有缺少的决定会实质改变结果、需要新授权或无法安全恢复时才请求用户。

主循环持续到以下任一终态：

1. 目标行为已经实现，相关验证通过，必要复审已结束，适用的 Git 交付已回读。
2. 下一步需要用户才能提供的权限、凭据、产品决定或外部状态；此时留下可恢复现场、已完成证据和唯一明确的解阻条件。
3. 用户明确改变范围或要求停止。

等待中的检查、构建或外部任务仍属于当前工作；继续观察到完成、失败或需要用户，不把“已启动”“已排队”写成完成。

## 自主完成循环

1. **建立事实。** 读取任务涉及的真实调用链、现有测试和仓库协议；检查并行改动，只处理本任务范围。
2. **实现最小完整方案。** 覆盖用户可观察结果及必要的错误路径，不顺手改造无关模块。
3. **取得直接证据。** 能复现原问题时先观察失败，再用同一路径观察修复；运行与改动风险相称的 lint、typecheck、test、build、运行时或界面验收。mock 只能证明 mock 覆盖的层级。
4. **独立复查。** 实质行为改动读取并执行 [joyally-loop](../joyally-loop/SKILL.md)；按 finding 做最小修正并复验。纯文本或无行为变化的小改动可以跳过，记录理由。
5. **完成交付。** 读取 `joy-git`，按用户、项目和全局已有授权决定 commit/push；本技能不创造额外 Git 权限，也不创建 PR。发布、部署、数据库迁移和其他高影响动作仍分别核验授权与真实结果。
6. **回读结果。** 核对最终 diff、验证输出、提交与远端状态；使用 `joyally-report` 区分实现、测试、Git 交付、部署和真实业务验收。

每次失败先定位原因并尝试安全、范围内且可验证的修正。相同阻塞重复出现时，不通过降低门槛或扩大权限伪造完成。

## 边界

- 普通工程完成不附带生产写入、正式发布、账号权限、数据删除、绕过保护或不可逆操作授权。
- 当前 checkout 有并行改动时保留它们；隔离和 Git 安全由 `joy-git` 处理，不把协作流程变成用户目标。
- 测试通过只证明对应测试；commit 或 push 也不证明部署和用户结果。
- 无法取得关键直接证据时，明确交付已完成到哪一层，以及补齐证据的条件。
