# Joyally Git

Git 收尾的目标是把本任务形成的、已验证且可追溯的改动交付到正确位置，同时保留并行工作，避免把一次代码修改自动扩大成发布、部署或危险的历史改写。先作决定，再执行动作；脏工作区或分叉是需要隔离的交付状态，不是默认停止理由。

## 先确定授权

依次读取用户当次要求、项目 `AGENTS.md` 或同类协议、全局约定和仓库当前状态。更具体、更新的要求优先。区分四种授权：

- 用户明确要求暂不提交或暂不推送：保留改动，报告位置与状态。
- 用户明确要求提交、推送或交付：在目标、分支和副作用清楚后执行；这不授权 force push、绕过保护或发布。
- 项目或全局协议明确授权任务完成后自动提交和推送：只有下方安全门通过时执行。
- 没有自动交付授权：可以准备和验证改动，但提交或推送前请求确认；不要从“请修复”“开始干”推导远端写入权限。

只读回答、诊断、评审和状态查询没有任务改动时，直接判定为 `no-action`。

## 建立任务边界

在编辑前和提交前分别检查仓库根目录、当前分支、HEAD、远端、upstream、作者身份以及 staged、unstaged、untracked 状态。若涉及多个仓库、submodule 或 worktree，逐个独立判断。

把文件分为：

1. 本任务产生或明确采用的改动；
2. 用户或并行任务的已有改动；
3. 生成物、缓存、凭据、日志和身份不明的改动。

只暂存第一类。逐文件查看差异与 staged 内容，使用显式路径暂存；已有 staged 改动也要确认归属。第二、三类保持原状并在交付中说明。仅有可分离的 unstaged/untracked 改动时，可以在当前 checkout 显式暂存任务文件；存在无关 staged 内容、当前分支分叉、detached HEAD 或其他会污染提交历史的状态时，保留原 index 和工作区，转入隔离交付。任务改动与并行改动在同一文件中时先尝试按明确 hunk 或补丁拆分；只有任务语义依赖无法拆开的并行内容时，才保留现场并请求决定。

## 隔离交付

自动交付已获授权且目标 ref 明确时，当前 checkout 不干净或分叉不得直接降级为 `leave-uncommitted` 或 `ask`。按项目协议说明任务、目录、临时分支、基线和原因，然后：

1. 获取目标远端的最新状态，以目标 ref 的确切 commit 创建独立 worktree 和任务专用本地分支；不 stash、reset、rebase 或改写原 checkout。
2. 只把本任务文件或可审查的任务补丁带入隔离 worktree。不得顺带复制原分支的其他 ahead commits、整个脏目录或身份不明的生成物。
3. 在隔离 worktree 重新运行必要验证，显式暂存任务文件并检查 staged diff。若任务依赖未提交的并行实现，先证明所需依赖范围；无法独立采用时才请求用户决定。
4. 推送前再次获取目标 ref。远端前进但没有语义冲突时，在未共享的任务分支上把任务提交重放到新基线并复验；有语义冲突或目标行为发生变化时才停止请求决定。
5. 以普通 fast-forward push 写入明确目标并回读远端 commit。确认原 checkout 仍包含本任务成果或明确其采用方式；远端已经采用且任务 worktree 干净后，清理本任务创建的临时 worktree 和本地分支，不触碰预先存在的 worktree。

隔离 worktree 和任务专用本地分支是完成已授权普通交付的实现手段，不新增发布权限，也不授权创建 PR、force push 或改写共享历史。

## 安全门

自动提交前必须同时满足：

- 改动符合用户要求和项目规范，没有意外文件、秘密、个人数据或不应进入版本历史的制品。
- 已运行与风险相称的验证；失败、跳过和未运行项已区分。关键门槛失败时不自动提交“完成版”。
- staged diff 只含本任务文件，`diff --check` 或项目等价检查通过，提交信息能描述实际结果。
- 作者身份符合仓库约定；不要为通过检查而猜测或全局改写身份。
- 仓库不处于未解决的 merge、rebase、cherry-pick 或冲突状态。

自动推送还必须满足：

- 当前分支和目标远端明确，不是 detached HEAD；远端跟踪关系与任务意图一致。
- 交付分支基于目标 ref 的当前远端状态，或已安全重放到该状态；普通 push 可以 fast-forward。原 checkout 的分叉不影响已隔离的交付，任何 force、删除远端分支或重写已共享历史仍需要用户明确授权。
- 推送不会未经授权地触发生产发布、正式发版、商店提交、数据库迁移或其他高影响外部动作。若仓库把普通 push 与这些动作绑定，按发布任务处理并单独确认授权。
- 凭据、签名、分支保护和 required checks 不需要绕过；失败时保留已完成的本地提交，报告恢复入口。

验证通过只证明对应测试或构建，不证明部署、分发、线上采用或真实业务结果。

## 作出一个决定

使用以下互斥结果：

| 结果 | 适用条件 | 动作 |
| --- | --- | --- |
| `commit-and-push` | 自动交付已获授权，提交与推送安全门全部通过 | 只提交任务改动，普通推送到明确目标并回读远端状态 |
| `commit-only` | 提交已独立获授权且安全，但推送未获授权、目标不明或会触发额外高影响动作 | 创建本地提交，报告 commit、分支和未推送原因；需要继续推送时再取得相应授权 |
| `leave-uncommitted` | 用户要求保留、验证尚未完成、改动仍是草稿，或隔离后仍无法把任务语义与并行改动拆分 | 不改变原 index 或历史，报告文件与下一步 |
| `no-action` | 没有本任务改动，或请求本来就是只读工作 | 不制造空提交，不推送无关既有提交 |
| `ask` | 缺少普通 commit/push 授权，或 force push、受保护分支、远端删除、身份、目标、真实语义冲突及无法先安全完成局部动作的发布副作用需要新决定 | 给出已尝试的隔离路径、具体对象、风险和所需决定，等待用户 |

网络暂时失败、认证失败或分支保护拒绝不自动改写为其他策略。保留本地提交并报告失败；只有安全、幂等且仍在原授权内时才重试普通 push。

## 执行与回读

执行获准动作时：

1. 提交前再次读取 `status`、工作区 diff 和 staged diff，确认任务文件完整且无夹带。
2. 运行最后的必要验证，记录实际通过、失败、跳过和环境限制。
3. 以显式路径暂存，提交后核对 commit 的文件清单与作者；hook 产生的新改动重新分类，不自动塞入原提交。
4. 推送前确认目标 ref；使用普通 push。推送后确认远端 ref 包含任务 commit，并再次检查工作区。
5. 按 [收尾结果契约](references/turn-report.md) 为每个仓库产出 Git 与交付事实；最终标题、列表、强调和代码样式由调用方的 Report 统一处理。

提交成功后出现他人的新提交或工作区变化，不把当前 branch tip 冒充本任务 commit；核对任务 commit 仍在远端祖先链中。部分仓库成功、部分失败时逐仓库报告，不把一次成功推广为全部完成。

## 边界

- 本技能不代替代码评审、测试选择、发布、部署或合并冲突处理；需要时使用项目已有流程。
- 不为了得到干净工作区而删除、还原、stash 或覆盖身份不明的改动。
- 不自动创建 PR、合并共享分支、打 tag、发 Release 或修改保护规则。可以为已授权交付创建任务专用本地分支和 worktree，并在远端采用且工作区干净后清理自己创建的临时资源；不清理预先存在的 worktree。
- 本技能判断 Git 交付动作，不把 commit 或 push 当成产品完成证据。

维护或实质修改本技能时，使用[行为检查](references/behavior-checks.md)复核关键分支；文字静态检查不能代替决策演练。
