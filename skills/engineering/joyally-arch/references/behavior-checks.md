# Behavioral checks for skill maintenance

Use when changing this skill's decision behavior. These are synthetic scenarios, not claims about a customer or the author's experience. Test actual answers and reference selection rather than headings or keyword matches.

Give an independent evaluator the current SKILL.md, a request below, and permission to read the skill's references. Keep this file's review criteria out of its prompt. Restrict the run to analysis and temporary artifacts; no customer contact, external mutations, or project implementation. Review the answer against the criteria afterward. Record failures and limits; a passing scenario does not prove all branches or real production behavior.

| Scenario to give the evaluator | Review criteria |
| --- | --- |
| A three-person team has 20 small-merchant pilots and 10,000 monthly support conversations, 70% about returns/exchanges. It wants fully automatic refunds and charging within six weeks. Inference is cheap; success, complaint, human cost, and authority data are unknown. Ask for business/product/architecture advice. | Distinguishes conversations from refundable cases; addresses payer, authority, domain rules, adoption and full handling cost; proposes a complete bounded slice and measurable next decision; preserves permissions, idempotency, reconciliation, and human recovery; invents no ROI or success baseline. |
| An established internal reporting tool has a stable 20-item configuration array, read once per build. There is no performance fault. Ask only whether to replace it with Map. | Gives a proportionate direct judgment grounded in lookup/maintenance semantics. Avoids a market study, unnecessary benchmarking, tests, or implementation work. |
| A B2B workflow product has 300 customers and six engineers. Two teams occasionally wait for each other's release; deployment is twice weekly. Capacity is unmeasured. A proposal asks for eight microservices for future growth. Ask for review and first delivery. | Examines the evidenced delivery bottleneck; compares modular monolith/selective extraction with the proposed split; accounts for data, operations and team cost; proposes a bounded useful slice, baseline, recovery and review trigger. |
| A GUI Agent's refund request times out and the remote effect is unknown. Product suggests immediate retry to improve success. Ask for execution boundaries, recovery, and validation. | Treats the outcome as uncertain, not failed; uses authoritative status, stable operation identity and verified remote idempotency; enforces authority outside the model; handles partial effects and manual reconciliation; tests through the formal entrypoint. |
| A pnpm project with existing customers wants mandatory global installation of its project-scoped CLI because docs become shorter. CI is unattended; targets are Windows and macOS. Ask for recommendation and verification scope. | Preserves project/lockfile authority, considers a thin optional launcher or package script, verifies non-TTY behavior and child-process evidence, and distinguishes platform acceptance. Does not reopen established product strategy. |
| A Node.js service's RSS is 200 MB at cold start and 800 MB after 24 hours. Ask whether this proves a leak and how to diagnose ongoing cost. | Requires comparable workload/lifecycle metrics, distinguishes heap/native retention and normal warmup, uses repeated lifecycle evidence and ownership analysis before micro-tuning, and states what remains unproven. |
| A team has 40 customer-support SOPs and wants to turn all of them into Skills so an Agent can refund automatically. Authority, errors, human costs, and outcome data are unknown. Ask for the first delivery. | Distinguishes reference knowledge, authoritative rules/code, and reusable Skill procedures; chooses a bounded complete workflow, models discovery and dependency failures, keeps authority explicit, and hands over runnable versions/evals/support without assuming a new platform. |
| A single Agent can demonstrate supplier reconciliation. The proposal is five Agents as a digital employee handling 500 cases daily, with finance handling exceptions. Ask for business/product and technical delivery design. | Treats capacity and multi-Agent benefits as unproven, defines the business duty and service/workload limits, authoritative reconciliation, task ownership and human handoff, and evaluates sustained accepted results, coverage, full cost and operating responsibility. |
| A deployed support Agent will change model, compress context, and update a refund Skill at once. Ten old cases used for prompt tuning now pass. Ask whether to release to every merchant and how to accept the release. | Separates development regressions from independent acceptance, checks partial/combined changes and run variation, binds runtime-loaded versions, tests context/permission failures and remote effects, and stages rollout with handoff plus result correction. |
| A browser Agent hides every ordinary form value behind a generic filled marker for privacy, then repeats fields after context compaction and fails to submit. Ask whether more runtime blocking is needed. | Restores authorized non-secret observation and durable value-free progress, keeps password isolation and irreversible-write checks at narrow boundaries, and rejects generic safety language as evidence for capability loss. |
| A schema-validated internal TypeScript handler needs one optional display label. A proposal adds repeated guards in four layers, three single-use helpers, a broad `try`/`catch`, and a mutex for a hypothetical concurrent reload. There is one call path and no observed concurrency failure. Ask for architecture review and implementation direction. | Keeps validation at the owning boundary and typed values inward; keeps cohesive single-use logic local; requires a distinct observable recovery outcome before adding exception handling; rejects the mutex absent a concrete failure and evidence. If a speculative race remains credible, states its failure mode, likelihood, complexity cost, and simpler mitigation, then seeks buy-in before expanding scope. |
| A single-tenant reporting job exports at most 5,000 rows each night. The existing service already owns the query, authorization and CSV library. A proposal adds an export microservice, queue, plugin interface and new deployment. Ask for the smallest complete architecture and what to defer. | Maps the full change surface, including the existing caller, authorization, output contract, tests, scheduling, failure visibility and support. Chooses the first complete reuse path instead of optimizing line count; keeps safeguards at their owning boundaries; rejects the service, queue and plugin without a current failure they solve. If synchronous or in-process export has a real ceiling, records the ceiling, measurable revisit trigger and credible upgrade path in an existing artifact. |
| A team has a one-sentence idea for an AI expense assistant, several later ideas, no verified integration, and no reason to choose cloud OCR yet. Ask to grow the architecture without writing a full PRD. | Keeps intent, verified facts, unresolved choices, deferred ideas, rejected paths, implementation, and acceptance distinct; focuses on the smallest end-to-end expense path and the decision that blocks it; proposes a bounded integration check; does not impose a graph, force every choice into A/B, or treat the architecture as implemented. |
| An established service has a large architecture map. One stable subsystem now exposes a narrow contract, while a new incident crosses that contract and contradicts an old assumption. Ask how to update the architecture. | Focuses on the incident's local upstream/downstream slice, updates verified reality and the affected decision, unfolds only the stable capability whose contract is crossed, preserves unrelated folded areas, records the invalidated path and acceptance gap, and avoids redesigning the whole system. |

On 2026-11-05, three independent GPT-6.1 Sol evaluators produced answers for two scenarios each. All six satisfied the scoped review criteria without an observed blocking behavior defect. The exercises checked reasoning, scope, and reference routing; no merchant trial, deployment, refund, CLI platform run, or memory experiment was executed. Raw evaluator output remained temporary. Re-run the affected cases after consequential changes; do not treat this result as a permanent quality guarantee.

Later on the same date, two independent evaluators exercised the three AI-specific scenarios added above and repeated the small configuration-array scenario. All four produced usable scoped answers without a blocking defect. Review exposed two useful clarifications, now incorporated: admission/coverage denominators and attribution of simultaneous AI changes. These are reasoning exercises, not evidence of real Skill execution, business trials, or production readiness.
