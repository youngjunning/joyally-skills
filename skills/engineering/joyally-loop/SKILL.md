# Joyally Loop

把一次工程改动闭环为“实现者完成 → 独立 reviewer 找真实问题 → 实现者核实并修正 → 重新验证”。目标是让当前任务可靠完成，不扩大需求，也不引入 PR 或分支流程。

## 进入条件

当任务改变运行行为、公共接口、权限、数据、状态、并发、构建或发布结果时，在主验证完成后自动进入本流程。用户也可以显式要求复审。只有文案、格式、注释或机械改名且已有充分检查时，可以跳过并说明原因。

## 固定审查范围

读取项目约定和当前工作区状态，只纳入本任务改动。以任务开始时的状态、当前 diff 和用户目标定义范围；保留并行改动，无法可靠区分时说明边界并停止审查。

首轮给 reviewer 提供：用户目标、范围外事项、任务 diff、必要上下文和已运行验证。reviewer 只审查，不编辑文件或执行 Git 交付，也不启动新的 reviewer。

## 有限轮次

- 默认最多 3 轮；只有安全、权限、认证、数据丢失、状态或并发风险仍有实证时，最多延长到 5 轮。
- 同一时刻只运行一个与实现上下文隔离的 reviewer。优先使用独立 agent；记录工具实际暴露的身份，不猜测模型。
- 维护 finding ledger：稳定 ID、严重度、主张、证据、处理结果。严重度只用 blocker、should、nit。
- reviewer 不可用、超时或失败都不算通过；确认旧 reviewer 已结束后才可重试。

首轮 reviewer 指令应包含：

```text
只评审当前任务改动，不修改文件，不执行 Git 交付，也不启动新的 reviewer。
核对用户意图、调用方、回归风险和验证证据；坚持最小改动。
按稳定 ID 返回 blocker / should / nit、文件位置、证据和最小修复建议，最后给 APPROVE 或 CHANGES。
```

## 核实与修正

实现者逐项独立核对 finding：

1. 事实成立时做最小修复；行为缺少覆盖时补一个没有修复就会失败的聚焦测试。
2. 事实不成立时，用文件位置、测试或可复现结果记录反证。
3. 范围外或纯 nit 记录理由，不为结束循环机械接受。
4. 每轮修正后重跑受影响检查，并更新 ledger。

只有 blocker 或 should 仍开放、行为代码又发生变化，或已有 approval 未覆盖当前 diff 时才进入下一轮。后续轮次只复查开放 finding 和新增变化。

## 结束条件

- **通过：** reviewer 明确 APPROVE 当前任务 diff，没有开放的 blocker 或 should，且实现者没有未解决疑虑。
- **阻塞：** 同一问题经过两次有证据的回应仍有分歧，独立 reviewer 持续不可用，或轮次预算耗尽。预算耗尽不是通过。

通过后把轮数、已解决和已驳回的 finding、验证结果交回主任务继续完成；阻塞时保留双方证据和最小待决问题。Git 提交、推送、部署和最终报告由对应流程独立处理。
