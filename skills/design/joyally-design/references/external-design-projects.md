# 外部设计项目提炼

当用户给出设计 Skill、组件库、提示词包或资源集合，并要求“吸收”“融合”“取精华”时使用本页。目标是把外部项目中能改变 Joyally Design 决策的机制放回现有流程，而不是复制整包规则、安装全部工具，或把收藏写成已经采用。

## 先确认对象

逐项核对原始仓库、当前提交、许可证与真正入口。海报名、转载名和搜索摘要只用于定位；结论来自仓库中的 `README`、`SKILL.md`、规范、脚本或组件源码。记录本轮读到的提交，区分四种状态：收藏、研究、采用、安装。收藏只保存回看线索；采用必须指出落入 Joyally Design 的哪条规则或哪个工具；安装还要有当前环境与真实调用证据。

## 五类可吸收机制

| 外部项目提供的能力 | Joyally Design 吸收什么 | 保留的边界 |
| --- | --- | --- |
| Taste Skill 的页面类型、主动作、真实素材与浏览器完成门禁 | 在动手前明确用户、页面承担的任务、一个主动作、可用真实素材和各区块职责；视觉手法必须适合产品类型 | 不照搬“一屏一节”、照片数量、动效数量等整包 house rules；目标项目与当前领域入口决定结构和密度 |
| UI UX Pro Max 的多域检索与版本感知建议 | 查询只围绕一个主问题：系统级方向查产品与品牌，局部问题查具体 UX 结果，落地问题再查技术栈；查询带产品、平台或交互约束 | 检索结果是候选证据，不是设计决定；不把风格、色板、字体和技术栈结果拼成自动套餐，不混用不同版本的实现建议 |
| Awesome DESIGN.md 的设计语言分析集合 | 用外部分析发现可比较的结构、角色和规则，并检查一份设计规范是否覆盖方向、颜色角色、字体、布局、深度、形状、组件、响应式与已知缺口 | 集合中的文件是对公开画面的第三方分析，不是品牌官方规范；必须回到当前网站或官方资料复核，不能复制品牌身份、商标、专有字体或整套视觉 |
| shadcn/ui 的 open code 与 Registry | 把组件源码作为目标项目本地拥有、可读可改的实现基础；从真实组件与组合控件建立页面，再映射项目语义 tokens 与状态 | 组件库不替代页面结构、内容策略与品牌方向；安装和更新前后都读本地差异，不能用 Registry 覆盖项目已经形成的业务变体 |
| Impeccable 的技术检测、设计评审与 `DESIGN.md` 提炼 | 把可确定检测、视觉判断和真实任务结果分开；检测命中先核对上下文，例外必须有当前产品依据；从代码、组件和渲染结果提炼规范并保留来源与缺口 | 未运行的检测不写成通过，零命中不等于设计合格；不接入上游 CLI、hooks、遥测或存储，除非用户另行要求并完成安装与隐私评估 |

## 做成一张采用账

每个候选机制写一行：

`来源与提交 | 原机制 | 当前证据 | 采用/不采用 | 落点 | 边界与验证`

- **采用**：必须落进现有唯一维护源，例如轻路径、领域入口、设计规范、组件工作流或质量门禁；已有等价规则时只补缺口，不再建同义规则。
- **不采用**：说明是场景不符、与项目约束冲突、只有主观样式偏好，还是需要尚未授权的运行时或外部服务。
- **无行为变化**：维持收藏或研究状态，不用新增文档制造“已经融合”的假象。

把外部规则改写为目标行为和完成条件，而不是保留上游命令、固定数量和营销语句。可以保留必要的来源链接、作者、许可证和提交；没有复制源码、素材或大段文本时明确写“方法研究，不含上游代码或资产”。

## 验收

1. 回读每个来源，确认名称、仓库、提交和许可证；列出的能力能在一手文件中找到。
2. 对照 Joyally Design 现有规则去重；每项采用都有唯一落点，并能说出它改变了什么决策。
3. 新规则继续服从用户要求、目标项目 `AGENTS.md`、现有品牌和平台约束；外部项目不能扩大权限或替换既有体验。
4. 修改 Skill 后运行仓库校验；若引入脚本、组件或资产，再运行对应测试并保留完整第三方许可证。规则校验通过只证明 Skill 结构，不证明任何真实页面已经改好。
